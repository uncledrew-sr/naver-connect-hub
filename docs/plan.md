# Briefy — 자연어 라이프 매니저

> **"한 문장으로 관리하는 하루"** — 자연어 한 줄로 적어내면 스케줄과 루틴이 정리되고, 브리핑까지 해주는 자연어 라이프 매니저

대학생의 하루에는 종류가 다른 할 일이 섞여 있다. 시간이 정해진 수업과 약속, 마감이 있는 과제와 공모전, 매주 반복되는 운동 루틴과 식단. 이걸 관리하려면 캘린더에 일정을 폼으로 입력하고, 리마인더에 과제를 적고, 오늘이 무슨 운동 하는 날인지는 메모 앱을 뒤져야 한다. 기록은 번거롭고, 조회는 흩어져 있다. 그래서 어느 순간 기록을 미루고, 미루다 놓친다.

**Briefy는 이 모든 과정을 문장 하나로 줄인다.** "금요일까지 데이터베이스 과제 제출"이라고 적으면 AI가 마감일 있는 과제로 분류해 저장한다. 폼도, 앱 전환도 없다. 수정과 조회도 같은 입력창에서 한다 — "치과 4시로 바꿔줘", "이번 주 마감 뭐 있어?"

그리고 아침에 앱을 열면 **오늘의 브리핑**이 기다린다. 오늘의 일정, 오늘 할 운동(시간만이 아니라 "상체 day · 러닝 3km"라는 내용까지), 오늘의 식단, 마감 임박한 과제가 한 화면에 모인다. 여러 앱을 오가던 아침 2분이 10초로 줄어든다.

자연어 입력이 편한 서비스는 있었고(Fantastical), 하루를 한눈에 보여주는 서비스도 있었다(Structured). 하지만 자유로운 문장으로 기록하는 것부터 하루를 통합해 보는 것까지를 하나의 경험으로 묶은 서비스는 없다. Briefy는 LLM 기반 자연어 파이프라인으로 그 공백을 메운다.

MVP는 자연어 CRUD와 브리핑 대시보드 두 기능에 집중하며, 웹(Next.js + Claude API)으로 빠르게 검증한 뒤 서버 전환과 모바일 앱으로 확장한다.

- **MVP**: 모바일 화면 기준의 웹 애플리케이션
- **최종 목표**: 모바일 애플리케이션 & 데스크탑 애플리케이션 (스마트폰 + 태블릿 + 랩탑)

> **구현 현황 (2026-07-24 갱신)**: 위 단락과 아래 6·7·8장 일부는 최초 기획 당시("웹은 Next.js + localStorage로 빠르게 검증한 뒤 Phase 2에서 서버로 전환") 그대로다. 실제로는 **Vite + React + Express + Supabase(Postgres)를 MVP(P0)부터 채택**해서 "서버 전환"이라는 별도 단계 없이 시작했고, LLM은 Claude API가 아니라 **Groq API**(`openai/gpt-oss-120b`)를 쓴다. 이 문서는 초기 의사결정 기록으로 그대로 두고, 실제 스택·진행 현황은 `AGENTS.md`와 `checklist.md`를 기준으로 본다. 아래 각 절에도 해당 지점에 갱신 메모를 남겨둔다.

## 1. 문제 정의

### 1.1. 본인 실제 사용 패턴에서의 불편함

일정, 과제 마감, 운동 루틴, 식단 등을 관리하는 대학생이, 고정 일정은 애플 캘린더에, 과제 마감과 메모는 리마인더에 나눠 기록하다가, 폼 입력의 번거로움(마감일과 반복 등)과 분산 조회의 불편함으로 관리하기가 까다롭다.

- **애플 캘린더**: 고정된 일정과 약속 등을 기록하지만, 마감일/반복/알림을 폼에서 하나하나 입력해야 하는 번거로움이 존재한다. 운동 루틴은 시간(20:00~21:00)만 등록될 뿐 오늘 어떤 운동 루틴(상체 day/하체 day)을 해야 하는지는 시각적으로 한눈에 들어오지 않는다.
- **애플 리마인더**: 마감일이 있는 과제와 마감일이 없어도 추후에 할 일들을 메모장처럼 기록한다. 리마인더가 캘린더에 통합 표시되긴 하지만 결국 캘린더에서 조회해야 하고, 두 앱을 오가는 관리 자체가 번거롭다.

**불편의 핵심**

1. 폼 입력이 귀찮다.
2. 일정/과제/루틴/식단이 흩어져 "오늘 하루" 또는 "이번 주"를 한눈에 볼 수 없다.
3. 루틴의 "내용"(오늘 할 운동, 오늘 식단)을 담을 곳이 없다.

### 1.2. 기존 서비스 사례 조사

| 서비스 | **Fantastical** | **Structured** |
| --- | --- | --- |
| 자연어 입력 | 자연어 처리 엔진이 있음 | 구조화된 폼 입력 |
| 통합 view | 기존 복잡한 캘린더 대시보드 형태 | 타임라인 형태로 단순화 |
| 서비스의 공백 | 통합 view가 많이 복잡한 형태 | 구조화된 폼 입력의 한계 |

> "자연어 입력이 강한 서비스는 통합 뷰가 약하고, 통합 뷰가 강한 서비스는 입력이 번거롭다 — 두 가지를 LLM 기반 자연어 파이프라인 하나로 묶은 서비스는 없다."

### 1.3. 타겟 사용자

고정 일정(수업, 약속), 마감이 있는 과제, 반복 루틴(운동, 식단)을 동시에 관리해야 하지만, 여러 도구를 오가며 불편함을 느끼는 대학생 및 사회초년생.

- 하루 단위로 해야 할 일이 3가지 이상의 서로 다른 성격(일정/과제/루틴)으로 섞여 있다.
- 기록 도구는 이미 쓰고 있지만(캘린더, 리마인더, 메모 앱 등), 입력이 번거로워 기록을 미루거나 누락한다.
- 일과를 시작하며 "오늘 뭐 해야 하지?"를 확인하기 위해 앱을 2개 이상 열어야 한다.

> 일정·과제·루틴을 함께 관리하는 대학생은 폼 입력의 번거로움과 분산 조회 때문에 기록과 확인을 반복적으로 누락하고, 결국 관리 자체를 포기하게 된다. 기존 서비스는 입력 편의(Fantastical)와 통합 조회(Structured) 중 하나만 해결하며, 규칙 기반 파싱의 한계로 루틴의 '내용'까지 담는 자유로운 문장 입력과 하루 통합 브리핑을 하나의 경험으로 제공하지 못한다.

### 1.4. 해결 방향

위 공백을 메우기 위해 Briefy는 두 가지에 집중한다.

1. **자연어 CRUD 파이프라인** — 폼 없이 문장 하나로 일정/과제/루틴을 등록·수정·삭제.
2. **오늘의 브리핑 대시보드** — 흩어진 항목을 하루 단위로 통합 조회.

## 2. 사용자 시나리오

### 2.1. 페르소나

**최범규 (25, 대학교 4학년)** — 매주 과제가 있는 전공 수업 3개, 팀 프로젝트 2개, 공모전 1개, 대외활동, 2분할 루틴과 러닝, 식단 관리를 하고 있다. 애플 캘린더와 애플 리마인더를 쓰고 있지만 폼 입력이 귀찮을 때가 많고 정보가 두 개의 앱으로 흩어져 있어 불편함이 존재한다. *(1.3 타겟 조건: 일정/과제/루틴 동시 관리 ⭕, 폼 입력 부담으로 기록 지연 ⭕, 조회 시 앱 2개 이상 필요 ⭕)*

### 2.2. AS-IS: 기존 방식

**아침 8시** — 오늘 할 일을 확인하려고 캘린더를 연다. 오후 3시 치과와 저녁 대외활동 정기 모임만 보인다. 전공 과제 3개와 공모전 제출 마감은 리마인더에 있어 앱을 전환한다. 오늘이 2분할 중 어느 날(상체/하체)인지, 러닝을 끼워야 하는 날인지는 어디에도 없다 — 캘린더엔 "운동 20:00" 블록뿐이다. 식단은 메모 앱 어딘가에 있다. **앱 3개를 오가며 약 2분.**

**수업 중** — 교수가 "금요일까지 과제 제출"이라고 공지한다. 리마인더를 열고 새 항목 → 제목 입력 → 날짜 탭 → 금요일 선택 → 저장, **탭 6회**. 팀플 회의 중엔 다음 회의 일정까지 캘린더에 따로 등록해야 한다. 귀찮아서 "나중에 적어야지" 하고 넘긴 날, 기록이 누락된다. 관리할 활동이 6종류다 보니 이런 입력이 하루에도 몇 번씩 생긴다.

**저녁** — 운동을 마쳤지만 완료 기록은 하지 않는다. 어디에 남겨야 할지 애매해서다. 다음 운동 날 "지난번이 상체였나 하체였나"를 기억에 의존해 되짚는다.

### 2.3. TO-BE: Briefy 사용

**아침 8시** — Briefy를 열면 오늘의 브리핑이 한 화면에 보인다: 오늘의 일정(15:00 치과, 19:00 대외활동 모임), 운동 루틴(20:00~22:00 · 상체 day + 러닝 3km), 오늘 식단(점심: 잡곡밥·닭가슴살 / 저녁: 삶은 달걀 3개·샐러드), 마감 임박 항목(공모전 서류 D-2, 전공 과제 3개 마감 빠른 순), 마감 없는 메모. **앱 1개, 10초.** 완료 체크 전까지 하루 내내 이 화면으로 돌아온다. *(→ 핵심 기능 B)*

**수업 중** — 공지를 듣자마자 입력창에 "금요일까지 데이터베이스 과제 제출"이라고 적는다. AI가 마감일 있는 과제로 자동 분류·저장한다. **문장 1개, 폼 입력 없음.** 팀플 회의가 끝나면 "다음주 화요일 오후 3시 팀플 회의, 전날 알려줘" — 일정과 리마인더가 동시에 생성된다. *(→ 핵심 기능 A)*

**점심시간** — 일정이 바뀌었다. "치과 4시로 바꿔줘"라고 입력하면 대상을 찾아 수정하고 확인 메시지를 보여준다. "이번 주 마감 뭐 있어?"라고 물으면 공모전 서류와 과제 2개만 골라 보여준다. 수정도 조회도 앱 전환 없이 입력창 하나에서 끝난다.

**오후, 모호한 입력** — 급하게 "운동"이라고만 입력했다. AI가 선택지 버튼을 제시한다: [오늘 운동 완료 기록] [할 일 추가] [루틴 수정]. **탭 1회로 확정.** 잘못 저장될 걱정 없이 짧게 던져도 된다.

**저녁** — 운동을 끝내고 "오늘 운동 다 함"이라고 입력하면 상체 day 루틴이 완료 체크된다. 완료 기록이 쌓이니 다음 운동 날 무엇을 할 차례인지 브리핑이 알려준다.

**다음 날 아침** — 새로 쌓인 항목까지 반영된 브리핑으로 하루를 시작한다. 6종류의 활동을 관리하는 비용이 사라지고, 활동 자체에 쓰는 시간만 남는다.

**이 시나리오로 검증하려는 가설**

1. 자연어 입력이 폼 입력 대비 기록 소요 시간과 누락률을 줄인다. *(탭 6회 → 문장 1개)*
2. 하루 통합 브리핑이 아침 조회 시간을 줄이고 재방문을 유도한다. *(앱 3개 2분 → 앱 1개 10초)*
3. 모호한 입력에 대한 선택지 제시가 오분류 불안을 낮춰 입력 빈도를 높인다.

## 3. 핵심 기능

Briefy의 MVP는 두 기능에 집중한다. 기능 A는 1.1의 불편 1·3(폼 입력의 번거로움, 루틴 내용을 담을 곳 없음)을, 기능 B는 불편 2(분산 조회)를 해결한다.

### 3.1. 기능 A — 자연어 CRUD 파이프라인

#### 3.1.1. 해결하는 문제

폼 기반 입력은 항목 하나에 탭 6회 이상이 필요하고, 일정/과제/루틴마다 입력하는 앱이 다르다. 이 마찰이 기록 지연과 누락으로 이어진다. *(← 1.1 불편 1, 3)*

#### 3.1.2. 동작 방식

사용자의 모든 입력은 단일 입력창을 거친다.

- **입력** → 자유로운 한국어 문장 (등록/수정/삭제/조회/완료 모두 동일 창)
- **처리** → (구현 현황: Claude API 대신 **Groq API**) 문장을 구조화된 JSON으로 파싱
  - 의도(intent: create/update/delete/query/complete) + 항목 유형(type: 일정/과제/루틴/식단/메모) + 속성(제목, 날짜, 시간, 반복, 리마인더, 내용)
- **출력** → (구현 현황: localStorage 대신 **Supabase**) 저장/반영 후, 무엇이 어떻게 처리됐는지 확인 카드 표시

#### 3.1.3. 단계별 구현 계획

전 단계가 하나의 자연어 파이프라인 위에서 동작하며, P0만으로 시연 가능한 최소선을 확보한다.

| 단계 | 내용 | 우선순위 |
| --- | --- | --- |
| A-1 | 저장 (파싱 → 분류 → 저장) + 되묻기 | P0 |
| A-2 | 조회 (질문형 입력 응답) | P1 |
| A-3 | 수정·삭제 (대상 식별 포함) | P1 |
| A-4 | 음성 입력 (STT) | Phase 2 |
| A-5 | 음성 대화 (AI가 음성으로 응답, TTS) | Phase 3 |

#### 3.1.4. 입력/출력 예시

| 사용자 입력 | 파싱 결과 |
| --- | --- |
| "금요일까지 데이터베이스 과제 제출" | create · 과제 · 마감 2026-07-10 |
| "다음주 화요일 오후 3시 팀플 회의, 전날 알려줘" | create · 일정(07-14 15:00) + 리마인더(07-13) 동시 생성 |
| "치과 4시로 바꿔줘" | update · 기존 항목 검색 → 시간 15:00→16:00 |
| "이번 주 마감 뭐 있어?" | query · 과제/일정 중 이번 주 마감만 필터 |
| "오늘 운동 다 함" | complete · 오늘의 루틴 인스턴스 완료 처리 |

#### 3.1.5. 예외 처리 (기능의 신뢰성 담보)

- **모호한 입력**: "운동"처럼 의도가 불분명하면 임의로 저장하지 않고 선택지 버튼 제시 → 탭 1회로 확정.
- **파싱 실패**: JSON 스키마 검증에 실패하면 원문을 '메모'로 보존하고 재입력 유도 — 사용자 입력은 절대 유실되지 않는다.
- **대상 불명확한 수정/삭제**: 후보가 2개 이상이면 목록을 보여주고 선택받는다.

#### 3.1.6. MVP 범위 밖 (Out of Scope)

음성 입력(A-4 · Phase 2), 음성 대화(A-5 · Phase 3), 영어 등 다국어 입력, 외부 캘린더(구글/애플) 동기화, 푸시 알림 발송

### 3.2. 기능 B — 오늘의 브리핑 대시보드

#### 3.2.1. 해결하는 문제

일정·과제·루틴·식단이 앱 3개에 흩어져 "오늘 하루"를 보려면 2분 이상 걸린다. 특히 루틴의 내용(오늘이 상체 day인지, 오늘 식단이 무엇인지)은 기존 도구 어디에도 담기지 않는다. *(← 1.1 불편 2, 3)*

#### 3.2.2. 동작 방식

- **입력** → 앱 접속 (별도 조작 불필요)
- **처리** → localStorage의 전체 항목 중 오늘 날짜 기준으로 필터링·정렬
  - 오늘 일정(시간순), 오늘의 루틴(반복 규칙에서 오늘 인스턴스 계산 — 예: 2분할 주기에서 오늘이 상체 day임을 도출), 오늘 식단, 마감 임박 과제(마감 빠른 순, D-day 표시), 리마인더(당일 도래분), 마감 없는 메모
- **출력** → 한 화면의 브리핑. 각 항목은 탭으로 완료 체크 가능, 완료 항목은 하단으로 이동
  > **구현 현황 (2026-07-24 갱신)**: "완료 항목은 하단 이동"은 실사용 중 두 차례 바뀌었다. ① 처음엔 완료 시 취소선+회색으로 제자리 유지(하단 이동 자체를 없앰). ② 이후 완료=아카이브 모델로 재변경 — 과제·메모를 완료 체크하면 브리핑에서 즉시 사라지고, 헤더의 화면 전환 버튼으로 들어가는 별도 완료함 화면에서만 조회·복구·영구삭제할 수 있다. 루틴은 이 모델과 무관하게 시간 순으로 항상 표시된다(완료 체크는 순환 계산용 로그일 뿐).

#### 3.2.3. 핵심 설계 포인트

- **루틴은 '시간'이 아니라 '내용'을 보여준다**: "운동 20:00"이 아니라 "상체 day · 벤치프레스, 러닝 3km" — 기존 캘린더와의 결정적 차별점
- **완료 상태가 다음 브리핑에 반영된다**: 오늘 상체 day를 완료하면 다음 운동일 브리핑에 하체 day가 표시됨 (루틴 순환)
- **브리핑이 곧 홈 화면**: 앱을 열면 항상 브리핑이 먼저 보이고, 기능 A의 입력창이 같은 화면 하단에 상주 — 조회와 입력이 한 화면에서 순환

#### 3.2.4. MVP 범위 밖 (Out of Scope)

주간/월간 뷰, 통계·리포트(운동 달성률 등), 브리핑 커스터마이징(섹션 순서 변경), 위젯

## 4. 데이터 모델

Briefy가 다루는 정보는 사용자의 입력이 분류되는 5가지 유형과, 이를 뒷받침하는 2개 보조 엔티티로 구성된다.

- **핵심 엔티티**: 일정(Schedule) · 과제(Task) · 루틴(Routine) · 식단(Meal) · 메모(Memo)
- **보조 엔티티**: 루틴 완료 이력(RoutineLog) · 리마인더(Reminder)

```
[Routine] 1 ── N [RoutineLog]      루틴의 완료 기록 → "다음은 하체 day" 계산에 사용
[Schedule/Task] 1 ── N [Reminder]  "전날 알려줘" 요청 시 부착
```

**설계 포인트 2가지**

1. **루틴은 시간이 아니라 '내용의 순환'을 저장한다** — 루틴 엔티티가 순환 내용(상체/하체)과 완료 이력을 가지므로, 기존 캘린더가 못 담던 "오늘 무슨 운동 차례인지"를 브리핑에 보여줄 수 있다. *(← 1.1 불편 3의 해결 근거)*
2. **모든 항목은 사용자 입력 원문을 보존한다** — 파싱이 잘못돼도 원문으로 복구 가능. *(← 3.1 "입력은 유실되지 않는다")*

상세 스키마는 `docs/data-model.md` 참조.

## 5. 화면 흐름

### 5.1. 화면 목록 (IA)

```
Briefy
├─ S1. 브리핑 홈 (메인, 앱 진입 시 항상 표시)
│   ├─ S1-a. 브리핑 영역 — 오늘의 일정 / 루틴(내용 포함) / 식단 / 마감 임박 / 메모
│   └─ S1-b. 입력창 (하단 상주) — 텍스트 입력
│
├─ S2. 입력 처리 상태 (S1 위에 오버레이/카드로 표시)
│   ├─ S2-a. 처리 중 표시
│   ├─ S2-b. 확인 카드 — "과제로 저장했어요: 데이터베이스 과제 (7/10 마감)"
│   ├─ S2-c. 되묻기 선택지 — 모호한 입력 시 버튼 제시
│   └─ S2-d. 대상 선택 — 수정/삭제 후보가 2개 이상일 때 목록 제시
│
├─ S3. 조회 결과 뷰 (질문형 입력의 응답, S1 내 임시 표시)
│
└─ S4. 항목 상세/편집 (브리핑에서 항목 탭 시)
```

독립된 페이지는 사실상 S1 하나이며, S2~S3은 S1 위에서 일어나는 상태 변화다. 이 구조 자체가 "조회와 입력이 한 화면에서 순환한다"(3.2)는 설계 의도의 구현이다.

### 5.2. 핵심 플로우 ① — 자연어 입력 (기능 A)

```
[S1-b 입력창] 문장 입력
    → [S2-a 처리 중]
    → 파싱 결과에 따라 분기:
        명확함              → [S2-b 확인 카드] → S1 브리핑에 즉시 반영
        모호함              → [S2-c 되묻기] → 탭 1회 → [S2-b] → 반영
        수정·삭제 대상 복수 → [S2-d 대상 선택] → [S2-b] → 반영
        파싱 실패           → 원문을 메모로 보존 + 재입력 안내 → S1
```

어떤 분기를 타든 **종착지는 항상 S1 브리핑**이다. 입력 결과가 브리핑에 바로 나타나는 것이 "기록→확인"의 보상 루프를 만든다.

### 5.3. 핵심 플로우 ② — 브리핑 조회와 완료 (기능 B)

```
앱 진입 → [S1 브리핑] 오늘 항목 확인
    → 항목 탭 → 완료 체크
        과제·메모 → 브리핑에서 사라짐 (완료함 화면에서만 조회, 복구/영구삭제 가능 — 구현 현황 3.2.2 참고)
        루틴 → RoutineLog 기록 → 다음 방문 시 다음 순환 단계 표시 (제자리 유지, 사라지지 않음)
    → (선택) 항목 상세 확인 → [S4] → S1 복귀
```

### 5.4. 와이어프레임

핵심 플로우에 등장하는 화면 중 다음 4개를 와이어프레임으로 제작한다: **S1(브리핑 홈), S2-b(확인 카드), S2-c(되묻기 선택지), S3(조회 결과)**. S4는 표준 상세 화면이므로 생략.

## 6. 플랫폼 전략

### 6.1. 판단 기준

MVP의 목표는 "자연어 입력이 폼 입력을 대체할 수 있는가"라는 가설 검증이다. 따라서 플랫폼 선택 기준은 세 가지: **검증까지의 개발 속도**, **배포·수정의 용이성**, **타겟 사용자의 접근 경로**.

### 6.2. MVP 레벨: 웹을 우선적으로 개발

| 기준 | 웹이 유리한 이유 |
| --- | --- |
| 개발 속도 | 단일 코드베이스, 익숙한 스택(구현 현황: Next.js 대신 **Vite + React** + Tailwind + TypeScript)으로 즉시 착수 |
| 배포·수정 | 스토어 심사 없이 배포, 파싱 프롬프트 개선을 실시간 반영 — LLM 기반 서비스는 초기 수정 빈도가 높음 |
| 접근 경로 | URL 하나로 테스트 유도 가능, 설치 장벽 없음. 모바일 브라우저 + 홈 화면 추가로 앱과 유사한 사용 흐름 확보 |

### 6.3. 고려한 대안과 배제 이유

- **네이티브 앱(iOS) 우선**: 타겟(대학생)의 주 사용 기기가 스마트폰이라는 점에서 유력했으나, 스토어 심사로 인한 수정 주기 지연과 개발 비용이 가설 검증 단계에 부적합해 배제. 모바일 경험은 반응형 웹으로 우선 커버한다.
- **크로스플랫폼(React Native) 즉시 시작**: 최종 목표 형태이지만, 웹 대비 초기 셋업 비용이 크고 MVP 검증에 불필요한 복잡도를 추가해 Phase 2로 이연.

### 6.4. 전환 계획과의 연결

웹에서 가설이 검증되면 React Native로 모바일 앱 전환한다(→ 7. 확장 계획). 이를 대비해 MVP 단계에서부터 **비즈니스 로직(파싱 처리, 브리핑 생성)을 UI와 분리**해 전환 시 로직 재사용이 가능하도록 설계한다.

## 7. 확장 계획

### 7.1. 단계별 로드맵

| Phase | 범위 | 진입 조건 |
| --- | --- | --- |
| **Phase 1 (MVP)** | 자연어 파이프라인(A-1~A-3) + 오늘의 브리핑, 웹, ~~localStorage~~ **(구현 현황: Express + Supabase를 P0부터 채택, 아래 참고)** | — (현재) |
| **Phase 2** | ~~서버 전환(FastAPI + DB + Docker)~~, 로그인/계정, 푸시 알림, 주간 뷰, 음성 입력(A-4, STT) | 핵심 가설 검증: 주 3회 이상 재방문 사용자 확보, 자연어 입력 성공률 90% 이상 |
| **Phase 3** | React Native 모바일 앱, 음성 대화(A-5, TTS), 외부 캘린더 동기화 | Phase 2 리텐션 유지 + 모바일 웹 접속 비중이 지배적임을 확인 |

> **구현 현황**: "서버 전환"은 Phase 2를 기다리지 않고 MVP(P0)에서부터 Express + Supabase(Postgres)로 이미 진행했다(FastAPI/Docker는 채택 안 함). 그래서 Phase 2는 실질적으로 로그인/계정·푸시 알림·주간 뷰·음성 입력만 남는다 — `checklist.md`의 Phase 2 절 참고.

### 7.2. 각 Phase의 논리

**Phase 2 — 서버 전환이 먼저인 이유** *(아래는 최초 기획 당시의 판단 근거 기록 — 실제로는 이 판단을 앞당겨서 서버 전환을 Phase 2가 아니라 MVP 단계에서 바로 했다)*: localStorage는 기기 종속이라 "여러 기기에서 내 브리핑 보기"가 불가능하고, 푸시 알림도 서버 없이는 못 보낸다. 즉 Phase 2의 기능들(계정, 알림)은 전부 서버 전환이라는 하나의 기술 전환에 묶여 있어 한 단계로 처리한다. 데이터 모델을 MVP부터 테이블 매핑 가능하게 설계한 것(4장)과, 로직-UI 분리(6.4)가 이 전환 비용을 낮춘다.

**Phase 3 — 앱 전환은 마지막인 이유**: 네이티브 앱의 가치(푸시, 위젯, 빠른 실행)는 이미 검증된 사용 습관이 있을 때 극대화된다. 습관이 검증되기 전의 앱 전환은 비용만 크다.

### 7.3. 하지 않을 것

확장 단계에서도 다음은 의도적으로 배제한다: **팀/공유 기능**(개인 관리 도구라는 정체성 유지), **범용 챗봇화**(일정 관리 외 잡담·검색 응답은 파이프라인의 정확도만 해침). 확장은 "관리 대상의 확장"(가계부, 수면 등)이 아니라 **"같은 대상을 더 잘 관리"**(통계 리포트, 루틴 추천) 방향을 우선한다.

### 8.2. 최대 리스크에 대한 입장

이 서비스의 성패는 결국 **파싱 신뢰도** 하나에 걸려 있다. 그래서 리스크 대응을 사후 대책으로 미루지 않고 **기능 설계 단계에 선반영**했다 — 되묻기를 P0에 포함(3.1.3), 원문 보존을 데이터 모델에 내장(4장), 확인 카드를 기본 UX로 채택. 남은 불확실성(실제 파싱 성공률)은 MVP 운영에서 성공률을 측정해 Phase 2 진입 조건(90%)으로 관리한다(7.1).
